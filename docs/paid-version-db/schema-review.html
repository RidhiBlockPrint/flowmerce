Review of the new Flowmerce database (paid version)

For the ERP team. This checks the flowmerce schema you shared against what Flowmerce needs (our spec: data-requirements.html), including the data Flowmerce uses today in Shipping, SEO and CRO and the planned Ads module. Reviewed 24 Nov 2026. Suggested SQL below is a starting point in your naming style; adjust it as you need.

Summary

The schema covers almost everything we asked for. Every row has workspace_id. Every source in our spec has tables. The design keeps customer personal data out: a hashed email only, and ship-to city, state and country only. All 10 Shopify analytics tables are there, and the DHL/FedEx tracking fields are complete.

Three things must be fixed before building on it:

  • M1: there is no table for outgoing changes and their approvals. ads_change refers to flowmerce.action, which is not in the schema.
  • M2: there is no general audit log.
  • M3: carrier scans have no unique key, so the same scan can be stored many times.

The export format ("for context only") does not show unique keys, indexes or row-level security, so those are listed under To confirm.

Must fix M1. No table for outgoing changes and approvals

Found: ads_change.action_id has a foreign key to flowmerce.action(id), but no action table is in the schema. There is also no approval table.

Why it matters: the paid version reads data from the database and uses APIs only to apply changes. Every change Flowmerce sends out needs one record that follows it: requested → approved → sent → done or failed, plus the API's answer. That covers publishing a blog article, uploading a file, changing product SEO, marking an order shipped, creating an MCF order, and pausing an ad or changing its budget. SEO's publish flow today also needs two different people (the requester and the approver) and a typed confirmation. Without this table, none of the write switches can be enforced or audited.

Please check first: was action cut off when the SQL was copied? If it exists, compare it with the fields below.

create table flowmerce.action (
  id              uuid primary key default gen_random_uuid(),
  workspace_id    uuid not null references flowmerce.workspace(id),
  store_id        uuid,
  module          text not null check (module in ('seo','shipping','cro','ads','catalog','system')),
  action_type     text not null,          -- 'shopify.article.publish', 'shopify.file.upload', 'shopify.product.seo_update',
                                          -- 'shopify.fulfillment.create', 'amazon.mcf.create_order',
                                          -- 'meta.adset.set_budget', 'google.campaign.pause', 'tracking.register', 'notify.send'
  switch_key      text not null,          -- which flowmerce.write_switch must be on
  target_type     text,                   -- 'seo_article', 'product', 'shop_order', 'ads_campaign' ...
  target_id       uuid,
  target_external_id text,
  request         jsonb not null default '{}',   -- exactly what will be sent
  request_hash    text not null,                 -- what was approved; sent only if unchanged
  status          text not null default 'requested' check (status in
                    ('requested','approved','rejected','queued','sending','succeeded','failed','cancelled')),
  requested_by    uuid,
  requested_at    timestamptz not null default now(),
  run_after       timestamptz,                   -- scheduled publish
  sent_at         timestamptz,
  finished_at     timestamptz,
  attempts        int not null default 0,
  response        jsonb,                         -- API answer (ids, URLs, errors)
  error           text,
  idempotency_key text not null,                 -- never send the same change twice
  unique (workspace_id, idempotency_key)
);

create table flowmerce.approval (
  id            uuid primary key default gen_random_uuid(),
  workspace_id  uuid not null references flowmerce.workspace(id),
  action_id     uuid not null references flowmerce.action(id),
  decided_by    uuid not null,
  decision      text not null check (decision in ('approve','reject')),
  confirm_text  text,                -- e.g. the typed word "PUBLISH"
  approved_hash text not null,       -- must equal action.request_hash
  note          text,
  decided_at    timestamptz not null default now()
);
-- Rule to enforce (trigger or backend): approver must be a different person from requested_by
-- for action types that need two people (Shopify publish, MCF create, ad budget).

create table flowmerce.approval_policy (
  workspace_id    uuid not null references flowmerce.workspace(id),
  action_type     text not null,
  needs_approval  boolean not null default true,
  two_person      boolean not null default false,
  min_role        text not null default 'manager',
  primary key (workspace_id, action_type)
);

Must fix M2. No general audit log

Found: catalog_change logs product, variant and collection changes only. Nothing records who changed a setting, a write switch, a member's role or stores, an alarm rule, an ads target, an exchange rate, a team mark or an article status.

Why it matters: a paid, multi-user product needs to answer "who turned on Shopify writes?" and "who changed this target?". Today's Flowmerce already keeps an audit log for SEO. For write switches it is essential, because a switch decides whether real changes reach Shopify, Amazon or the ad platforms.
create table flowmerce.audit_log (
  id            bigint generated always as identity primary key,
  workspace_id  uuid not null references flowmerce.workspace(id),
  store_id      uuid,
  at            timestamptz not null default now(),
  actor_type    text not null check (actor_type in ('user','job','system','api')),
  actor_id      uuid,                   -- user id when actor_type = 'user'
  actor_label   text,                   -- job name, e.g. 'sync.shopify.orders'
  entity_type   text not null,          -- 'write_switch','setting','member','seo_article','ads_target' ...
  entity_id     text not null,
  verb          text not null,          -- 'create','update','delete','approve','publish','login'
  before        jsonb,
  after         jsonb,
  ip            inet,
  note          text
);
create index on flowmerce.audit_log (workspace_id, at desc);
create index on flowmerce.audit_log (workspace_id, entity_type, entity_id, at desc);
-- Append-only: grant insert/select only; no update/delete for app roles.

Must fix M3. Carrier scans can be stored twice

Found: flowmerce.scan has no external_id and no unique key except its own uuid.

Why it matters: every tracking check (Shopify, DHL, FedEx, Amazon, the sheet) returns the full scan history again. Without a key, each check adds the same scans again. That inflates scan_count, shows the same event many times, and breaks the rule that a parcel's status is its newest scan by scanned_at.
alter table flowmerce.scan add column external_id text;   -- carrier/Shopify event id; if none, a hash of
                                                         -- (tracking_id, scanned_at, raw_status, city)
alter table flowmerce.scan add column raw jsonb;          -- the event as received (no personal data)
create unique index scan_one on flowmerce.scan (tracking_id, external_id);
create index scan_newest on flowmerce.scan (tracking_id, scanned_at desc, received_at desc);

Should add S1. Status map can't tell Shopify's word from the carrier's

Found: status_map is keyed by carrier_code (not null) and raw_status, with is_delivery_proof.

Why it matters: Shopify says "DELIVERED" for a DHL parcel, and DHL also says "delivered". Only DHL's word is proof of delivery; Shopify's is not. With carrier as the only key, both rows would be (dhl, DELIVERED), so the two can't be told apart. Shopify words also apply to every carrier, which needs an "any carrier" row.
alter table flowmerce.status_map add column source text not null default 'carrier'
  check (source in ('shopify','carrier','aggregator','amazon','mcf_sheet','manual'));
-- allow '*' = any carrier (add a carrier row with code '_any', or make carrier_code nullable)
create unique index status_map_one on flowmerce.status_map
  (coalesce(workspace_id,'00000000-0000-0000-0000-000000000000'), source, carrier_code, raw_status);
-- Rule: source = 'shopify' rows must have is_delivery_proof = false.

We can send the full list of status words we use today: Shopify, DHL Unified API, FedEx Track API codes and the tracking-service tags.

Should add S2. Sessions per product (ShopifyQL) are missing

Found: the sq_* tables cover sessions by device, channel, country, region, landing page and hour, and sales per product. They have nothing for sessions and add-to-cart per product viewed.

Why it matters: the CRO product screen shows, for each product, how many sessions viewed it and how many added it to cart (ShopifyQL sessions … GROUP BY viewed_product). This shows which products get visits but don't sell. ga4_product_daily is a different count (GA4 rather than Shopify) and is not always connected.
create table flowmerce.sq_product_sessions_daily (
  workspace_id        uuid not null,
  store_id            uuid not null,
  day                 date not null,
  product_external_id text not null,
  product_id          uuid references flowmerce.product(id),
  device              text not null default 'all',
  sessions            integer not null default 0,
  sessions_with_cart  integer not null default 0,
  sessions_reached_checkout   integer not null default 0,
  sessions_completed_checkout integer not null default 0,
  is_final            boolean not null default false,
  pulled_at           timestamptz not null default now(),
  primary key (store_id, day, product_external_id, device)
);

Should add S3. No way to escalate alerts to a team head

Found: team has only a name, and member has a role (owner…viewer). Today's Flowmerce (ops.people) has team, title and is_head. Alerts not answered within 4 working hours go to the head of that step's team, then to the owner. Working hours are also used for alert clocks.

Why it matters: order_event has owner_team, assigned_to and due_at, but nothing says who the head of a team is, so escalation can't work.
alter table flowmerce.team add column head_user_id uuid;      -- must be a member of the workspace
alter table flowmerce.team add column code text;              -- 'production','shipment','orders','care','corporate'
alter table flowmerce.member add column title text;
-- order_event.owner_team stays text and holds team.code
-- working hours / escalation rules live in flowmerce.setting (keys 'working_hours', 'escalation').

Should add S4. AI images and uploaded files aren't recorded

Found: ai_job holds the text AI jobs. There is no record of AI image generations (prompt, reference photos, result, cost per image) or of files uploaded to Shopify Files (the file id and URL an article uses).

Why it matters: SEO already makes banner and Pinterest images and uploads them to Shopify. Each image costs money and must be traceable to its article. Uploads also need to be checked so the same image isn't uploaded twice.

Either confirm that images are ai_job rows with job_type = 'image' (input = prompt + reference URLs, output = image URL, cost_usd), or add:

create table flowmerce.media_file (
  id               uuid primary key default gen_random_uuid(),
  workspace_id     uuid not null,
  store_id         uuid not null,
  origin           text not null check (origin in ('upload','ai_generated','shopify_sync')),
  ai_job_id        uuid references flowmerce.ai_job(id),
  shopify_file_id  text,                 -- set after fileCreate succeeds (via flowmerce.action)
  url              text,
  alt_text         text,
  width            int, height int, bytes int, mime_type text,
  sha256           text,                 -- stops uploading the same image twice
  used_by_type     text, used_by_id uuid, -- e.g. seo_article
  created_by       uuid,
  created_at       timestamptz not null default now(),
  unique (store_id, sha256)
);

Should add S5. Ads targets don't cover all the measures used

Found: ads_target.metric allows only roas, cpa, ctr, cpm, frequency and daily_spend_cap.

Why it matters: the Meta screens are modelled on our three Ridhi sheets (daily report, creative scorecard, ABO-to-CBO gap). Those also judge CPC, hook rate (3-second views ÷ impressions), hold rate (ThruPlays ÷ 3-second views), and cost per add-to-cart and per checkout. They also use a warning level between target and breakeven.
alter table flowmerce.ads_target drop constraint ads_target_metric_check;
alter table flowmerce.ads_target add constraint ads_target_metric_check check (metric in
  ('roas','cpa','ctr','cpm','cpc','frequency','daily_spend_cap',
   'hook_rate','hold_rate','cost_per_atc','cost_per_checkout'));
alter table flowmerce.ads_target add column warn_value numeric;
alter table flowmerce.ads_target add column platform text check (platform in ('meta','google'));  -- null = both
alter table flowmerce.ads_target add column note text;

Should add S6. Reship and "done" flags from order notes

Found: shop_order correctly has no note text. But today's Shipping board uses two facts it derives from the note and tags: whether the order is a reship / replacement of another order (and which one), and whether the team wrote DONE in the note.

Why it matters: without these, reshipped orders show up as new unshipped orders, and finished orders stay on the board. We keep only the derived facts, never the note text.
alter table flowmerce.shop_order add column is_reship boolean not null default false;
alter table flowmerce.shop_order add column reship_of_order_name text;   -- e.g. '#R1234', taken from tags/note
alter table flowmerce.shop_order add column note_done boolean not null default false;

Security

  • Row-level security on every table, with policies by workspace_id (and member_store when all_stores = false). Includes the raw_* tables.
  • Members only see costs (variant.cost, ship_cost, ship_rate_card, ai_job.cost_usd) when can_see_costs = true, through views or column grants.
  • The browser key (anon) can read nothing; sync jobs use the service key on the server only.
  • connection.secret_name points to Supabase Vault; no secret value in any table.

Other

  • Is anything after ai_job_event missing from the paste (e.g. action, see M1)?
  • raw_api_payload is partitioned by received_at. What is the retention (we proposed 13 months)? Same question for raw_webhook_event, carrier_call (proposed 90 days) and scan (keep).
  • updated_at triggers on tables that have the column.
  • Indexes for the main screens: shop_order (store_id, src_created_at desc), tracking (workspace_id, active, next_check_at), scan (tracking_id, scanned_at desc), every *_daily (store_id, day), order_event (order_id, at desc).
  • tracking.status rule: delivered must have delivered_at, and delivery_confirmed is true only when the source can confirm delivery (not Shopify).

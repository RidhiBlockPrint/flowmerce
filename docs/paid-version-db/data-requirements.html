Flowmerce paid version: data we need stored

For the team building the new database on the separate Supabase account. It lists what data Flowmerce needs, where it comes from, how much history, how often it refreshes, and which changes go back out through APIs. Prepared 24 Nov 2026 from the current Flowmerce code.

1. The rule: store first, APIs only to change things

Today some Flowmerce screens ask Shopify, GA4 and others live on every page view. In the paid version that stops:

  • Every screen reads only our database. No page waits on an outside API.
  • Sync jobs and webhooks fill the database on a schedule. Every run is logged so each screen can show "data as of …".
  • APIs are used to apply changes, such as publishing an article, changing an ad budget or marking an order shipped. Each change is recorded as an action, approved where needed, and its result is written back to the database.
  • If an API is down or rate-limited, screens keep working on the last stored data and show how old it is.
Legend used below: stored today already kept in a database · live today read from the API on each view, must become stored · not built planned, no code yet.

2. Ground rules for every table

  • Workspace id on every row. A paid version serves many businesses, so each row carries workspace_id (the paying customer) and store_id (one of their stores), with row-level security on both. Our assumption; confirm.
  • Platform id next to our id. Keep the outside id as text, with (provider, external_id) unique, so a re-sync updates rows instead of making duplicates.
  • Raw copy of every answer. Keep each API/webhook payload in a raw table (with retention), so data can be rebuilt without asking the API again.
  • Sync log and cursor per source and store: started, finished, rows read/written, error, cursor, and a lock so the same job never runs twice at once.
  • Time zone and currency. Store timestamptz; store each money value in its own currency, with the currency code. Daily figures use the account's own day (an Indian ad account and a US store have different days).
  • Re-pull window. Ads, analytics and Search Console revise recent days, so jobs re-read the last 3–10 days every run.
  • Secrets never in tables. Tokens and keys live in Supabase Vault or the host's secret store; tables hold only the name of the secret.
  • Write switches. Every kind of outside change has an on/off setting, off by default.
  • Audit. Every change by a person or a job is logged: who, when, old value, new value.

4. Shopify (Admin GraphQL + webhooks)

Orders stored today

  • Order: id, number/name, created, updated, cancelled (time + reason), test flag, financial status, fulfillment status, tags, source/channel, landing site and referrer (for UTM / ad attribution), discount codes, shipping method chosen, ship-to city / state / country only.
  • Money (shop currency and presentment currency): subtotal, discounts, shipping, tax, total, total refunded, net.
  • Lines: line id, product id, variant id, SKU, title, quantity, unit price, discount, fulfilled quantity, product type, tags.
  • Fulfillments: id, status, display status, created, in-transit at, estimated delivery, delivered at, service (manual / Amazon fulfillment), carrier name as written, tracking numbers and URLs, which lines went in which parcel.
  • Fulfillment events: id, status, happened at, message, city, state, country.
  • Refunds and returns: refund amounts, lines, reason; return status and return tracking.

How: webhooks orders/create, orders/updated, orders/cancelled, fulfillments/create, fulfillments/update, fulfillment_events/create, refunds/create, returns/*, plus a 15-minute catch-up by updated_at and a bulk export for backfill. Today Flowmerce keeps only 60–120 days; the paid version should keep everything.

Catalog and stock live today

  • Products: id, handle, title, type, vendor, tags, status, online store URL, featured image, SEO title/description, created/updated.
  • Variants: id, SKU, barcode, price, compare-at price, cost, weight, inventory item id.
  • Collections and which products are in each.
  • Inventory levels per location (also used to warn when ads promote a product that is low on stock).
  • Shop: name, domains, time zone, currency, plan.

How: webhooks products/*, collections/*, inventory_levels/update, plus a full re-list every 6 h that removes products Shopify no longer has.

Blog stored today

Blogs (id, handle, title) and articles (id, title, handle, body, summary, tags, author, published / publish date, image + alt text, SEO title and description metafields), including drafts made in Shopify.

6. Google Search Console and GA4

  • Search Console stored today: clicks, impressions, CTR, position by date × page, and by page × search query (28-day periods). Today only /blogs/ pages; the paid version should take the whole site (product, collection and landing pages too). 16 months of history (Google's limit), ending 3 days ago.
  • GA4 pages stored today: sessions, engaged sessions, engagement rate, engagement time, key events by date × landing page.
  • GA4 products live today: item views and add-to-carts by date × item id, matched to the Shopify product id.
  • Rows loaded from Excel or by hand are kept apart from API rows (a source column), so a re-sync never deletes them.

7. Meta Ads and Google Ads not built

Read-only for version 1. Four accounts today (2 platforms × 2 brands). A full draft table design is in ads_reference.sql (see section 15).

  • Accounts: id, name, currency, time zone, status, which store it belongs to.
  • Structure: campaigns (objective / channel type, status, delivery status, budget, CBO or ABO, bid strategy, dates), Meta ad sets / Google ad groups and asset groups (budget, optimisation goal, learning stage, targeting), ads, creatives (format, text, headline, CTA, link, image/thumbnail, video length), Google keywords (match type, status, quality score).
  • Daily numbers per account / campaign / ad set / ad: spend, impressions, reach, frequency, clicks, link clicks, landing page views, add to cart, checkout, payment info, purchases, purchase value, 3-second video views, ThruPlays, video 25/50/75/100%, search impression share; plus the platform's full action list as JSON.
  • Breakdowns: age, gender, placement, platform, device, country, region, hour.
  • Google search terms by day.
  • Change history: Meta activity log and Google change events (who changed what, when, old/new value).
  • Counting rules found while testing: Meta funnel counts must use the omni_ action types (these matched our sheets). Google "conversions" include non-purchase actions, so store conversion actions with a "counts as purchase" flag and count only those.
  • Ours, typed in: targets (ROAS, CPA, CTR, frequency …), exchange rate used for USD ↔ INR, with the date it applies from.
  • Joined to Shopify: orders matched to campaigns through UTM / landing site, so platform-reported sales can be compared with real store sales.

8. Shipping and carriers (DHL, FedEx, others)

Today Shipping knows only what Shopify says, and Shopify's "delivered" is not proof. The paid version should ask the carriers directly. A full draft design is in carrier_tracking_reference.sql.

  • Tracking numbers stored today: carrier, number, our status (pending / info received / in transit / out for delivery / delivered / exception / returned / expired), raw carrier status, picked up, last scan, ETA, delivered at, delivery confirmed (true only from a carrier), team mark (lost, delivered, failed …) kept apart from carrier data.
  • Scans: every event with time, status, message, city, state, country; never stored twice.
  • From DHL / FedEx not built: service, weight, pieces, ETA window, signed by, proof of delivery, customs status, exception code and text.
  • Status word map as a table (carrier word → our status), so a wrong mapping is fixed as data, not code.
  • Carrier name map (e.g. "DHL Express", "dhl" → DHL), because Shopify carrier names are typed freely.
  • Every carrier call logged and counted per day, to stay under each carrier's daily limit.
  • Also planned: problems/exceptions, claims, returns, shipping costs and rate cards.
  • Open choice: ask DHL and FedEx directly, or use one tracking service (AfterShip / 17TRACK) that covers all carriers.

9. Amazon Multi-Channel Fulfillment

  • stored today Copied once a day from the team's Google Sheet: brand, order number, MCF id, order status, received, speed, parcel, carrier, tracking, shipped, arrives by, current status, last scan, where, delivered, checked, flag.
  • not built Better: Amazon SP-API directly (needs Seller Central API access): MCF orders, shipments, packages, tracking events, FBA stock per SKU. Tables already drafted in 109_amazon_mcf_intake.sql.

10. AI usage stored today

  • Each AI job: type (topic research, draft, revision, image prompt, CRO advice …), input, output, status, events, model, tokens, cost.
  • Daily spend per workspace, with a budget limit.
  • Image generations: prompt, reference images used, result, cost.

11. Data the team types in stored today

This data exists only in Flowmerce, so it must be stored and backed up:

  • SEO: topics, keywords, articles and every revision, review notes, approvals, publish requests, schedule, brand settings, automation state.
  • Shipping: order marks (reviewed, flagged, outcome), notes, team marks on parcels, settings (working hours, step limits, escalation).
  • CRO: alarm rules, alerts, change log, recommendation status, experiments, goals, free-shipping amount, saved AI advice.
  • Ads: targets, exchange rates.
  • People: users, roles, teams, which stores and sections each person sees, who may see costs.

13. What we never store

  • Customer names, emails, phone numbers, street addresses or order note text. Only city, state, country, and where needed a hashed email (to tell new from returning customers).
  • From carriers: only the "signed by" name, no receiver address beyond city / state / country.
  • API tokens, keys and passwords (secret store only).
  • Note: today's schema still has some unused customer columns (ops.orders: customer_name, email, phone, address). Leave them out of the new design.

14. Open questions to settle before building

  • Is the paid version multi-customer (needs workspace_id everywhere), or one database per customer?
  • Webhooks need a public URL that is always on. Where will it run, and who receives them?
  • How long to keep raw API answers (proposal: 13 months), and scans and call logs (proposal: 90 days for call logs)?
  • DHL + FedEx direct, or one tracking service for all carriers?
  • Amazon: SP-API access (Seller Central developer registration) or keep the sheet?
  • Ads: exchange-rate rule (the sheets use ₹88 and ₹95 per $1), which targets are official, whether to exclude bulk orders.
  • Who fills the current hub tables (public.orders) today, and does that move into the paid version?
